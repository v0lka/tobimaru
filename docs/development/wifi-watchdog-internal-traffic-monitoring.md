## Tobimaru WiFi Watchdog — Мониторинг внутреннего трафика: техники и аномалии

### Контекст и позиция наблюдателя

Tobimaru подключён к защищаемой сети через managed-интерфейс (или Ethernet). Он является обычным участником L2-сегмента и может пассивно наблюдать:

- **Broadcast/multicast трафик** — ARP, mDNS, SSDP, DHCP, NetBIOS, IGMP — видим полностью, без каких-либо дополнительных условий.
- **Unicast трафик к/от шлюза** — если сеть построена на обычном WiFi-роутере (не управляемый свитч), то в WiFi-сегменте весь трафик идёт через AP и теоретически доступен при promiscuous mode на managed-интерфейсе. Однако WPA2/WPA3-шифрование на уровне unicast фреймов означает, что чужой unicast расшифровать нельзя, если не знать PTK сессии каждого клиента.
- **DNS-запросы** — если DNS-сервер = роутер (что характерно для домашних сетей), DNS-запросы идут в L2-сегменте к роутеру. В случае, если агент стоит на самом роутере или получает зеркало трафика (port mirroring), видимость полная. Иначе — только собственный DNS-трафик и broadcast.

**Практический вывод:** наиболее реалистичная позиция для домашней сети — агент работает *на роутере* (OpenWrt, Raspberry Pi в роли роутера) или получает трафик через port mirroring / ARP-based interception. Альтернативно — агент выступает DNS/DHCP-сервером для сети, что даёт полную видимость DNS-запросов и DHCP-lease.

### Техники наблюдения

#### 1. Пассивный DNS-мониторинг

**Что наблюдаем:** все DNS-запросы от устройств в сети (A, AAAA, CNAME, TXT, MX, SRV, PTR записи).

**Как получаем доступ:**
- Агент является DNS-resolver'ом сети (задаётся через DHCP option 6) — самый надёжный вариант, полная видимость.
- Перехват DNS на порту 53 через iptables redirect (если агент на роутере).
- Прослушивание broadcast DNS (mDNS на порту 5353) — даёт информацию о сервисах, но не о внешних запросах.

**Что можно извлечь:**
- Полный список доменов, к которым обращается каждое устройство.
- Временные паттерны запросов (периодичность, объём).
- Типы запросов (необычно высокий объём TXT-запросов — признак DNS tunneling).
- Ответы с NXDOMAIN (характерно для DGA).

#### 2. Анализ сетевых потоков (NetFlow-like)

**Что наблюдаем:** метаданные соединений — source IP/port, destination IP/port, протокол, объём данных, длительность, количество пакетов.

**Как получаем доступ:**
- На роутере: conntrack table (Linux netfilter) через `conntrack -L` или netlink.
- При наличии port mirroring: gopacket на зеркальном интерфейсе, агрегация в flow records.
- На самом хосте: анализ ARP + наблюдение за broadcast позволяет понять, кто активен, но не видеть unicast flows.

**Что можно извлечь:**
- Граф коммуникации: кто с кем разговаривает (внутри сети и наружу).
- Объёмы трафика per-device.
- Профиль портов назначения (подозрительные порты: 4444, 8080, высокие нестандартные).
- Количество уникальных внешних IP, с которыми общается устройство.

#### 3. ARP-мониторинг

**Что наблюдаем:** все ARP-запросы и ответы в сегменте (broadcast).

**Как получаем доступ:** пассивный захват на любом интерфейсе в том же L2-сегменте — ARP всегда broadcast.

**Что можно извлечь:**
- Полный реестр устройств (MAC→IP binding).
- Появление новых устройств.
- ARP-аномалии: spoofing (несколько MAC для одного IP), gratuitous ARP storms, ARP-запросы к несуществующим IP (сканирование подсети).

#### 4. DHCP-мониторинг

**Что наблюдаем:** DHCP Discover/Offer/Request/Ack (broadcast на портах 67/68).

**Как получаем доступ:** пассивный захват broadcast.

**Что можно извлечь:**
- Hostname, vendor class (идентификация устройства).
- Факт получения адреса новым устройством.
- Rogue DHCP server (Offer от неожиданного источника).
- Аномально частые DHCP-запросы (MAC spoofing, DHCP exhaustion).

#### 5. mDNS/SSDP/NetBIOS мониторинг

**Что наблюдаем:** multicast service discovery (Bonjour, UPnP, NetBIOS).

**Как получаем доступ:** пассивный захват multicast.

**Что можно извлечь:**
- Каталог сервисов, которые анонсирует каждое устройство.
- Появление неожиданных сервисов (HTTP-сервер на IoT-устройстве, которое его раньше не имело).
- Fingerprinting устройств по набору анонсируемых сервисов.

#### 6. Анализ TLS-метаданных (при видимости unicast)

**Что наблюдаем:** TLS ClientHello (SNI, JA3/JA4 fingerprint, поддерживаемые cipher suites).

**Как получаем доступ:** только при наличии видимости unicast (port mirroring, роутер-позиция).

**Что можно извлечь:**
- Домены, к которым идёт HTTPS-подключение (из SNI, даже без DNS).
- JA3/JA4 fingerprint клиента — позволяет идентифицировать библиотеку/framework (малварь часто имеет характерный JA3, отличный от браузеров).
- Необычные cipher suite preferences.

### Аномалии для детектирования

#### Категория A: C2-коммуникации (Command & Control)

| Аномалия | Индикатор | Метод детектирования |
|----------|-----------|---------------------|
| **Периодические beacon'ы** | Регулярные соединения к одному IP/домену с фиксированным интервалом (±jitter) | Статистический анализ интервалов между соединениями; коэффициент вариации < порога |
| **DNS beaconing** | Периодические DNS-запросы к одному домену | Анализ timestamps DNS-запросов per-domain; FFT или autocorrelation |
| **DGA-домены** | Большое количество NXDOMAIN-ответов; домены с высокой энтропией имени | Подсчёт NXDOMAIN per-device; Shannon entropy имён; длина домена; consonant/vowel ratio |
| **DNS tunneling** | Аномально длинные поддомены; TXT-запросы к нетипичным доменам; высокий объём DNS-трафика | Средняя длина query name; доля TXT/NULL-запросов; байт/с в DNS per-device |
| **Обращение к известным C2-инфраструктурам** | Подключения к IP/доменам из threat intelligence feeds | Сопоставление с публичными blocklists (abuse.ch, OpenPhish, etc.) |

#### Категория B: Lateral Movement (распространение внутри сети)

| Аномалия | Индикатор | Метод детектирования |
|----------|-----------|---------------------|
| **Внутреннее сканирование портов** | Устройство пытается подключиться к множеству портов на другом хосте | Подсчёт уникальных dst-портов per src-dst pair за период |
| **Сканирование подсети** | ARP-запросы к последовательным IP-адресам | Подсчёт ARP who-has per-device за период; детектирование sweep-паттернов |
| **Нехарактерные внутренние соединения** | IoT-устройство обращается к другому IoT по SSH/SMB/RDP | Baseline разрешённых внутренних пар; детектирование новых flows |
| **Pass-the-hash/credential relay** | SMB/NTLM-аутентификация между хостами, которые раньше не общались | Мониторинг новых SMB-сессий (порт 445) |

#### Категория C: Data Exfiltration (утечка данных)

| Аномалия | Индикатор | Метод детектирования |
|----------|-----------|---------------------|
| **Аномальный объём upload** | Устройство отправляет значительно больше данных, чем обычно | Baseline per-device upload volume; Z-score anomaly |
| **Подключения к необычным GeoIP** | Соединения с IP в странах, с которыми устройство раньше не общалось | GeoIP lookup + baseline per-device geography |
| **Ночная активность** | Передача данных в нетипичное время (IoT-камера в 3 часа ночи шлёт 500MB) | Временной профиль активности per-device; anomaly в off-hours |
| **DNS exfiltration** | Кодирование данных в поддоменах DNS-запросов | Длина subdomain > порога; энтропия subdomain; объём DNS per-device |

#### Категория D: Нарушение поведенческого baseline

| Аномалия | Индикатор | Метод детектирования |
|----------|-----------|---------------------|
| **Новый внешний endpoint** | Устройство впервые обращается к IP/домену, который не в его историческом профиле | Per-device whitelist endpoints после learning phase; alert на новые |
| **Новый используемый протокол/порт** | Устройство впервые использует порт/протокол (напр. IoT-лампочка открывает SSH наружу) | Per-device baseline портов; alert на новые |
| **Резкий рост числа соединений** | Rate connections/minute значительно превышает baseline | Скользящее среднее + стандартное отклонение; Z-score |
| **Смена JA3 fingerprint** | То же устройство начинает использовать другую TLS-библиотеку | Привязка JA3 к MAC/IP; alert при смене |
| **Изменение DNS-профиля** | Набор запрашиваемых доменов резко отличается от исторического | Cosine similarity текущего DNS-профиля с baseline |

#### Категория E: Специфичные IoT-аномалии

| Аномалия | Индикатор | Метод детектирования |
|----------|-----------|---------------------|
| **IoT-устройство стало сканером** | Лампочка/камера шлёт ARP/TCP SYN к устройствам в сети | Подсчёт уникальных dst per-device; порог для IoT-класса |
| **Участие в DDoS** | Резкий рост исходящих SYN-пакетов или UDP-потоков к одному IP | Rate outbound connections per-device; detection of SYN-heavy traffic |
| **Криптомайнинг** | Постоянная TCP-сессия на нестандартном порту с фиксированным низким bandwidth | Pattern: long-lived connection + small periodic data exchange + stratum protocol ports (3333, 8333) |
| **Неожиданное обновление firmware** | Большой download с нехарактерного источника | Per-device download baseline; alert на большие transfers с новых IP |

### Архитектурный подход к baseline

Для поведенческой аналитики необходимо:

**Learning phase (первые N дней после установки):**

1. Агент наблюдает за сетью и строит per-device профили: набор доменов, типичные endpoints (IP:port), объёмы трафика (upload/download per hour), временной профиль активности, ARP-поведение, набор протоколов.
2. Каждый профиль хранится как набор метрик со скользящими средними и отклонениями.
3. В learning phase детектор работает в режиме наблюдения и не генерирует alerts (кроме критических — известные C2, DGA).

**Detection phase (после завершения обучения):**

1. Каждое наблюдение сравнивается с профилем устройства.
2. Отклонение выше порога (configurable) → событие безопасности.
3. Профиль продолжает медленно обновляться (exponential moving average) — адаптация к естественным изменениям поведения.

### Что реализуемо на уровне проекта (без ML-моделей)

Все вышеперечисленные техники детектирования реализуемы **чистой статистикой и правилами**, без необходимости тренировки ML-моделей:

- **Пороговые правила:** NXDOMAIN count > N, DNS query length > M, connections/min > K.
- **Скользящие средние + Z-score:** для объёмов трафика, количества соединений, количества уникальных endpoints.
- **Periodicity detection:** коэффициент вариации интервалов (CV < 0.2 → подозрительная периодичность); альтернативно — autocorrelation на ряде timestamps.
- **Энтропия:** Shannon entropy для имён доменов (DGA-домены: H > 3.5–4.0).
- **Whitelist/baseline:** после learning phase — простое сравнение с множеством known-good.
- **Threat intelligence matching:** загрузка публичных lists (abuse.ch URLhaus, Feodo Tracker) и проверка IP/доменов.

### Зависимость от позиции агента

| Позиция агента | Видимость | Применимые техники |
|---|---|---|
| **На роутере (OpenWrt / RPi-router)** | Полная: весь трафик проходит через агент | Все техники; максимальное покрытие |
| **DNS-сервер сети** | DNS-запросы всех устройств; broadcast | DNS-мониторинг, ARP, DHCP, mDNS |
| **Обычный хост в WiFi-сети** | Только broadcast + свой трафик | ARP, DHCP, mDNS/SSDP; ограниченная видимость |
| **Хост + port mirroring** | Полная (зависит от настроек mirror) | Все техники |

**Рекомендация для проекта:** поддержать все позиции, но документировать различия в покрытии. Минимальный полезный набор (ARP + DHCP + mDNS) работает из любой позиции. DNS-мониторинг требует специальной настройки. Flow analysis — позиции на роутере или port mirroring.
