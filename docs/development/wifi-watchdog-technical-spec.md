# Система защиты беспроводной сети Tobimaru WiFi Watchdog

## Общие требования

Tobimaru представляет собой систему мониторинга и защиты домашней WiFi-сети, состоящую из агента-сенсора и веб-дашборда. Агент работает на хосте с WiFi-адаптером, захватывает и анализирует беспроводной трафик в пассивном режиме, детектирует подозрительную активность и предоставляет информацию об окружении через REST API и веб-интерфейс.

### Агент (сенсор)

Агент должен реализовывать следующую бизнес-логику:

- переключение WiFi-адаптера в режим мониторинга (monitor mode) с поддержкой платформ Linux и macOS;
- захват 802.11-фреймов в неразборчивом режиме (promiscuous/monitor mode);
- парсинг management-, control- и data-фреймов стандарта 802.11;
- построение и поддержание карты радиоокружения: обнаруженные точки доступа (BSSID, SSID, канал, тип шифрования, уровень сигнала) и клиентские устройства (MAC, привязка к AP, уровень сигнала);
- переключение каналов (channel hopping) для покрытия наблюдением всех каналов диапазона;
- детектирование атак на беспроводную сеть на основе сигнатурных и статистических правил;
- классификация обнаруженных событий по уровню угрозы;
- хранение истории событий и состояния окружения в локальной базе данных;
- управление whitelist/blacklist MAC-адресов;
- оповещение о событиях безопасности через настраиваемые каналы (webhook);
- предоставление REST API для взаимодействия с веб-дашбордом.

### Веб-дашборд

Веб-дашборд должен реализовывать следующую бизнес-логику:

- отображение текущей карты радиоокружения в реальном времени (список AP, клиентов, их параметры);
- отображение ленты событий безопасности с фильтрацией по типу, уровню угрозы и времени;
- визуализация статистики: количество событий по типам, временные графики активности;
- управление конфигурацией агента: защищаемый SSID, whitelist/blacklist, пороги детектирования;
- отображение состояния агента (статус захвата, текущий канал, uptime);
- пользовательские роли user (только наблюдение и оповещения) и admin (конфигурация сервиса).

### Функции, реализация которых остаётся на усмотрение исполнителя

- выбор формата и схемы локальной базы данных;
- алгоритм и стратегия channel hopping (порядок каналов, время пребывания на канале);
- конкретные пороговые значения для сигнатурных и статистических правил детектирования;
- протокол real-time обновления дашборда (polling, SSE, WebSocket);
- способы аутентификации и авторизации доступа к веб-дашборду;
- формат конфигурационного файла агента;
- фреймворк и библиотека для реализации фронтенда дашборда;
- механизм развёртывания и управления жизненным циклом агента (systemd unit, launchd plist и т.д.).

### Дополнительные требования

- агент должен компилироваться и работать на платформах Linux (amd64, arm64) и macOS (arm64, amd64);
- различия в возможностях платформ (см. раздел «Платформенные ограничения») должны обрабатываться через абстракцию: отсутствие возможности не должно приводить к ошибке запуска;
- агент должен предоставлять информацию о версии и дате сборки бинарного файла;
- веб-дашборд должен обслуживаться встроенным HTTP-сервером агента (single binary deployment).

## Типы детектируемых атак

### Обязательные к детектированию

- **Deauthentication flood** — массовая отправка deauth-фреймов, направленная на отключение клиентов от AP;
- **Disassociation flood** — аналогичная атака с использованием disassociation-фреймов;
- **Evil Twin AP** — появление точки доступа с SSID, совпадающим с защищаемой сетью, но с отличающимся BSSID, каналом или набором Information Elements;
- **Beacon flood** — массовое появление фиктивных точек доступа (резкий рост уникальных BSSID);
- **Unauthorized device** — появление в эфире клиентского устройства, отсутствующего в whitelist, ассоциированного или пытающегося ассоциироваться с защищаемой AP.

### Обнаружение атак через анализ EAPOL (при условии наблюдения за handshake)

- **WPA Handshake capture attempt** — аномальный поток EAPOL-фреймов, особенно в сочетании с предшествующими deauth-фреймами;
- **PMKID harvesting** — появление EAPOL-фреймов msg1 от неизвестных клиентов без продолжения handshake.

Для любого обнаруженного события должна сохраняться следующая информация: временная метка, тип атаки, уровень угрозы (info/warning/critical), MAC-адреса участников, канал, уровень сигнала (при наличии), дополнительные метаданные (количество фреймов, продолжительность и т.д.).

## Платформенные ограничения

Реализация должна учитывать различия платформ:

| Возможность                      | Linux                            | macOS                                    |
| -------------------------------- | -------------------------------- | ---------------------------------------- |
| Monitor mode                     | Полноценный (через `iw`/netlink) | Ограниченный (через `airport`/CoreWLAN)  |
| Channel hopping                  | Нативный                         | Через системные утилиты, с ограничениями |
| Frame injection                  | Поддерживается                   | Не поддерживается                        |
| Одновременное подключение к сети | Возможно (второй интерфейс)      | Не поддерживается                        |

Агент должен корректно определять доступные возможности платформы при запуске и адаптировать своё поведение: на macOS injection-функции должны быть отключены, channel hopping может работать с увеличенными интервалами, а информация об ограничениях должна быть доступна через API и отображаться в дашборде.

## Абстрактная схема взаимодействия с системой

Ниже описаны базовые сценарии взаимодействия пользователя с системой. Они не являются исчерпывающими — решение отдельных сценариев (например, поведение при невозможности переключить адаптер в monitor mode) остаётся на усмотрение исполнителя.

### Первый запуск

1. Пользователь устанавливает агент на хост с WiFi-адаптером.
2. Пользователь указывает в конфигурации защищаемый SSID и адаптер для мониторинга.
3. Агент переключает адаптер в monitor mode и начинает захват.
4. Агент строит начальную карту окружения (discovery phase).
5. Пользователь открывает веб-дашборд и видит обнаруженные AP и клиентов.
6. Пользователь формирует whitelist доверенных устройств (вручную или через auto-learning).

### Повседневная работа

1. Агент непрерывно захватывает фреймы и обновляет карту окружения.
2. При обнаружении подозрительной активности агент создаёт событие безопасности.
3. Событие сохраняется в базу данных, отправляется в настроенные каналы оповещения и появляется в реальном времени на дашборде.
4. Пользователь просматривает событие, анализирует детали и при необходимости корректирует whitelist или пороги детектирования.

### Обнаружение атаки (на примере Evil Twin)

1. Агент обнаруживает beacon-фреймы с SSID, совпадающим с защищаемой сетью, но от неизвестного BSSID.
2. Агент сравнивает Information Elements нового AP с эталонным fingerprint защищаемой AP.
3. При расхождении — создаётся событие уровня critical с указанием BSSID, канала и RSSI нарушителя.
4. Событие отображается в дашборде, отправляется webhook-оповещение.

## Тестирование и документация

Код всей системы должен быть покрыт юнит-тестами не менее чем на 70%. Каждая экспортированная функция, тип, переменная, а также пакет системы должны содержать исчерпывающую документацию.

Для модуля детектирования атак должны быть подготовлены тестовые pcap-файлы (или их генераторы), моделирующие каждый тип обнаруживаемой атаки — для обеспечения воспроизводимого тестирования detection engine без реального радиоэфира.

## Необязательные функции

Перечисленные ниже функции необязательны к имплементации, однако позволяют лучше оценить степень экспертизы исполнителя. Исполнитель может реализовать любое количество из представленных ниже функций на свой выбор:

- **активное противодействие (frame injection):** отправка deauth-фреймов для отключения атакующих устройств от защищаемой сети или от Evil Twin AP (только Linux);
- **мониторинг внутренней сети через второй интерфейс:** подключение к защищаемой сети через managed-интерфейс для обнаружения ARP spoofing, rogue DHCP, DNS spoofing;
- **терминальный интерфейс (TUI):** интерактивный терминальный интерфейс для мониторинга состояния и управления агентом без веб-браузера;
- **обнаружение KARMA/Known Beacons атаки:** детектирование AP, отвечающих на probe request с произвольным SSID;
- **обнаружение WPA downgrade:** детектирование попыток клиента ассоциироваться по WPA2 при наличии WPA3 на защищаемой AP;
- **device fingerprinting:** идентификация устройств по совокупности probe request IE, OUI, поведенческих паттернов;
- **поведенческая аналитика:** построение baseline нормального трафика и обнаружение аномалий статистическими методами;
- **поддержка push-оповещений через Telegram Bot API;**
- **наличие функциональных и/или интеграционных тестов;**
- **описание REST API агента в формате OpenAPI (Swagger);**
- **поддержка нескольких агентов** с агрегацией данных на одном дашборде (distributed sensing).
