# Руководство пользователя

Данное руководство охватывает установку, настройку и запуск Tobimaru на Linux и macOS.

## Установка

### Сборка из исходного кода

Требования:

- Go 1.26 или новее (модуль объявляет `go 1.26.3`)
- GNU Make
- Node.js 22+ и `npm` — нужны только при пересборке встроенного веб-дашборда

```bash
git clone https://github.com/vkochetkov/tobimaru.git
cd tobimaru
make build
```

Собранный бинарный файл размещается в `bin/tobimaru`. Заранее собранный бандл
дашборда зафиксирован в `internal/api/web/dist/`, поэтому `make build`
производит полнофункциональный бинарь без выполнения `make web`. Запускайте
`make web-deps && make web` только при изменении исходников SPA.
`make web-deps` необходимо выполнить перед `make web` для установки TypeScript и других Node-зависимостей.

### Кросс-компиляция

Сборка бинарных файлов для всех поддерживаемых платформ:

```bash
make build-all
```

Результат:

- `bin/tobimaru-linux-amd64`
- `bin/tobimaru-linux-arm64`
- `bin/tobimaru-darwin-arm64`

## Настройка платформы

### Linux

1. Определите имя WiFi-интерфейса:

   ```bash
   iw dev
   ```

   Типичные имена: `wlan0`, `wlp2s0`, `wlan1` (внешний адаптер).

2. Убедитесь, что утилиты `iw` и `ip` установлены:

   ```bash
   # Debian/Ubuntu
   sudo apt install iw iproute2

   # Fedora/RHEL
   sudo dnf install iw iproute
   ```

3. Запускайте от имени root (необходимо для режима мониторинга):

   ```bash
   sudo ./bin/tobimaru -config configs/tobimaru.yaml
   ```

### macOS

Поддержка macOS имеет ряд ограничений:

- Невозможен захват трафика при подключении к WiFi на том же адаптере.
- Нет инъекции фреймов (активные контрмеры недоступны).
- Переключение каналов занимает 1–3 секунды — увеличьте `dwell`.
- Требуются разрешения на доступ к BPF-устройствам (запуск от root).
- Переключение каналов выполняется через встроенный CoreWLAN-мост — утилита
  `airport` не нужна.

Шаги настройки:

1. Определите WiFi-интерфейс (обычно `en0`):

   ```bash
   ifconfig | grep -B2 "status: active"
   ```

2. Отключитесь от WiFi перед началом захвата (macOS не может мониторить при
   подключении на том же адаптере).

3. Запустите от root:

   ```bash
   sudo ./bin/tobimaru -config configs/tobimaru.yaml
   ```

4. Рекомендуемые настройки конфигурации для macOS:

   ```yaml
   monitor:
     channel_hopping:
       dwell: 2s # Увеличить с 300ms из-за медленного переключения каналов
   ```

Рецепты ChmodBPF и LaunchDaemon описаны в `docs/development/macos-setup.md`.

## Конфигурация

Tobimaru читает YAML-файл конфигурации. Скопируйте аннотированный пример как
отправную точку:

```bash
cp configs/tobimaru.yaml tobimaru.yaml
```

Значение `-config` по умолчанию — `configs/tobimaru.yaml`. Передайте `-config`
для указания собственного пути.

### Справочник по конфигурации

#### `log` — Логирование

| Поле     | Тип    | По умолчанию | Описание                                                                |
| -------- | ------ | ------------ | ----------------------------------------------------------------------- |
| `level`  | string | `info`       | Уровень логирования: `debug`, `info`, `warn`, `error`                   |
| `format` | string | `text`       | Формат вывода: `text` (человекочитаемый) или `json` (структурированный) |

#### `monitor` — WiFi-интерфейс

| Поле        | Тип    | По умолчанию | Описание                                                         |
| ----------- | ------ | ------------ | ---------------------------------------------------------------- |
| `interface` | string | —            | **Обязательное.** Имя WiFi-интерфейса (например, `wlan0`, `en0`) |

#### `monitor.capture` — Захват пакетов

| Поле                | Тип      | По умолчанию | Описание                              |
| ------------------- | -------- | ------------ | ------------------------------------- |
| `snaplen`           | int      | `65535`      | Максимальное количество байт на фрейм |
| `buffer_size`       | int      | `2097152`    | Размер буфера ядра в байтах (2 МБ)    |
| `frame_buffer_size` | int      | `1024`       | Ёмкость канала распарсенных фреймов   |
| `promiscuous`       | bool     | `true`       | Включить неразборчивый режим          |
| `timeout`           | duration | `100ms`      | Таймаут чтения для pcap-хэндла        |

#### `monitor.channel_hopping` — Сканирование каналов

| Поле            | Тип      | По умолчанию | Описание                              |
| --------------- | -------- | ------------ | ------------------------------------- |
| `enabled`       | bool     | `true`       | Включить переключение каналов         |
| `dwell`         | duration | `300ms`      | Базовое время на каждом канале        |
| `channels_2ghz` | []int    | `[1..13]`    | Каналы 2.4 ГГц для сканирования       |
| `include_5ghz`  | bool     | `false`      | Включить сканирование диапазона 5 ГГц |
| `channels_5ghz` | []int    | —            | Каналы 5 ГГц (при включении)          |

#### `monitor.channel_hopping.weighted_dwell` — Приоритетные каналы

| Поле               | Тип   | По умолчанию | Описание                                         |
| ------------------ | ----- | ------------ | ------------------------------------------------ |
| `enabled`          | bool  | `true`       | Увеличить время удержания для основных каналов   |
| `primary_channels` | []int | `[1, 6, 11]` | Каналы с увеличенным временем удержания          |
| `multiplier`       | float | `2.5`        | Множитель времени удержания для основных каналов |

Основные каналы (1, 6, 11) — наиболее часто используемые неперекрывающиеся
каналы 2.4 ГГц. Взвешенное удержание выделяет им больше времени мониторинга.

#### `detection` — Движок обнаружения

| Поле                | Тип      | По умолчанию | Описание                                                 |
| ------------------- | -------- | ------------ | -------------------------------------------------------- |
| `enabled`           | bool     | `false`      | Главный переключатель движка обнаружения                 |
| `dedup_window`      | duration | `30s`        | Подавлять дублирующиеся оповещения в пределах этого окна |
| `alert_buffer_size` | int      | `256`        | Ёмкость буферизированного канала оповещений              |

Движок поставляется с пятью правилами. Каждое правило настраивается под
ключом `detection.<rule_name>`:

| Правило             | YAML-ключ             | `enabled` по умолчанию | Описание                                                         |
| ------------------- | --------------------- | ---------------------- | ---------------------------------------------------------------- |
| Deauth flood        | `deauth_flood`        | `true`                 | Скользящее окно по deauth-фреймам                                |
| Disassoc flood      | `disassoc_flood`      | `true`                 | Скользящее окно по disassoc-фреймам                              |
| Beacon flood        | `beacon_flood`        | `true`                 | Всплеск уникальных BSSID после learning-периода                  |
| Evil Twin           | `evil_twin`           | `true`                 | Расхождение SSID/BSSID/IE по score-порогу                        |
| Unauthorized device | `unauthorized_device` | `false`                | Whitelist-проверка; требует `protected_bssids`/`protected_ssids` |

Общие поля правил:

| Поле               | Тип      | Описание                                                   |
| ------------------ | -------- | ---------------------------------------------------------- |
| `enabled`          | bool     | Включение/выключение правила                               |
| `threshold`        | int      | Порог срабатывания (flood-правила)                         |
| `window`           | duration | Размер скользящего окна (flood-правила)                    |
| `learning_period`  | duration | Начальный период без алертов (`beacon_flood`, `evil_twin`) |
| `score_threshold`  | int      | Накопленный score перед алертом (`evil_twin`)              |
| `stale_timeout`    | duration | Удалять AP не наблюдавшиеся это время (`evil_twin`)        |
| `min_beacons`      | int      | Минимум beacon'ов перед оценкой (`evil_twin`)              |
| `protected_bssids` | []string | BSSID защищаемых AP (`unauthorized_device`)                |
| `protected_ssids`  | []string | Защищаемые SSID (`unauthorized_device`)                    |
| `whitelist`        | []string | Разрешённые MAC клиентов (`unauthorized_device`)           |
| `alert_on_probe`   | bool     | Алертить на probe request (`unauthorized_device`)          |
| `cooldown`         | duration | Подавление по MAC (`unauthorized_device`)                  |

Установите `detection.enabled: true`, чтобы начать получать оповещения.
Поставляемый `configs/tobimaru.yaml` оставляет детектирование выключенным,
чтобы демон можно было прогонять в режиме чистого захвата.

#### `state` — Движок состояния сети

| Поле             | Тип      | По умолчанию | Описание                                      |
| ---------------- | -------- | ------------ | --------------------------------------------- |
| `enabled`        | bool     | `true`       | Хранить AP и клиентов в памяти                |
| `ttl`            | duration | `10m`        | Удалять записи, не наблюдавшиеся дольше этого |
| `sweep_interval` | duration | `1m`         | Интервал eviction-сканирования                |

Отключение состояния также отключает снапшоты, auto-learning и stateful-зависимые
страницы дашборда.

#### `whitelist.auto_learning` — Авто-обучение

| Поле       | Тип      | По умолчанию | Описание                            |
| ---------- | -------- | ------------ | ----------------------------------- |
| `enabled`  | bool     | `false`      | Запускать learning-режим при старте |
| `duration` | duration | `15m`        | Длительность фазы обучения          |

В learning-режиме каждое наблюдаемое устройство добавляется во in-memory
whitelist (и сохраняется в БД, если `storage.enabled`).

#### `storage` — SQLite-хранилище

| Поле                | Тип      | По умолчанию  | Описание                                                |
| ------------------- | -------- | ------------- | ------------------------------------------------------- |
| `enabled`           | bool     | `false`       | Главный переключатель SQLite-хранения                   |
| `path`              | string   | `tobimaru.db` | Путь к файлу БД (создаётся с правами `0600`)            |
| `snapshot_interval` | duration | `5m`          | Период снапшотов состояния                              |
| `max_snapshots`     | int      | `288`         | Хранение снапшотов (~24ч на 5-минутном шаге)            |
| `max_events`        | int      | `100000`      | Хранение событий безопасности (prune раз в 100 вставок) |

Tobimaru использует pure-Go SQLite-драйвер (без CGO). Файл создаётся или
chmod-ится в `0600` при открытии.

#### `api` — HTTP API + дашборд

| Поле                       | Тип      | По умолчанию     | Описание                                                          |
| -------------------------- | -------- | ---------------- | ----------------------------------------------------------------- |
| `enabled`                  | bool     | `false`          | Запустить HTTP-сервер и обслуживать дашборд                       |
| `listen`                   | string   | `127.0.0.1:8080` | Адрес привязки (для удалённого доступа используйте reverse proxy) |
| `read_timeout`             | duration | `15s`            | HTTP read timeout                                                 |
| `write_timeout`            | duration | `30s`            | HTTP write timeout (SSE отключает его per-request)                |
| `idle_timeout`             | duration | `60s`            | Idle keep-alive timeout                                           |
| `shutdown_timeout`         | duration | `5s`             | Дедлайн graceful HTTP shutdown                                    |
| `cors.allowed_origins`     | []string | `[]`             | Пусто = только same-origin                                        |
| `auth.enabled`             | bool     | `true`           | Требовать вход в дашборд и API                                    |
| `auth.session_ttl`         | duration | `24h`            | Время жизни сессионного токена                                    |
| `auth.admin_password_hash` | string   | —                | bcrypt-хэш; обязателен при `auth.enabled: true`                   |
| `auth.user_password_hash`  | string   | —                | Опциональный read-only аккаунт; пусто отключает его               |

При `auth.enabled: true` обязательно `storage.enabled: true`, так как сессии
сохраняются в SQLite.

### Валидация конфигурации

Tobimaru валидирует конфигурацию при запуске со строгим парсингом:

- Неизвестные YAML-ключи отклоняются (никаких тихих сбоев из-за опечаток).
- `monitor.interface` обязателен — запуск завершится ошибкой без него.
- Числовые значения должны быть положительными, где это применимо.
- Все ошибки валидации выводятся одновременно через `errors.Join`.

### Минимальная конфигурация

```yaml
monitor:
  interface: wlan0
```

Все остальные поля используют разумные значения по умолчанию.

## Запуск

### Флаги командной строки

| Флаг             | Описание                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------- |
| `-config <путь>` | Путь к YAML-файлу конфигурации (по умолчанию: `configs/tobimaru.yaml`)                               |
| `-version`       | Вывести информацию о версии и завершить работу                                                       |
| `-hash-password` | Запросить пароль интерактивно (без вывода на экран) и вывести его bcrypt-хэш, затем завершить работу |

Этот флаг — встроенная утилита для генерации bcrypt-хэшей, которые
помещаются в YAML-конфигурацию. Пароли никогда не хранятся открытым текстом —
поля `auth.admin_password_hash` и `auth.user_password_hash` принимают только
заранее захэшированные bcrypt-значения. Флаг запрашивает пароль интерактивно
(без отображения на экране), поэтому пароль не появляется в списке процессов
или истории командной оболочки. Скопируйте вывод в конфиг. Внешние инструменты
(htpasswd, python-скрипты) не требуются.

### Базовое использование

```bash
# Запуск с явным указанием конфигурации
sudo ./bin/tobimaru -config /etc/tobimaru/tobimaru.yaml

# Вывод версии
./bin/tobimaru -version
# Вывод: Tobimaru v1.0.0 (commit: abc1234, built: 2026-01-15T10:30:00Z)

# Сгенерировать bcrypt-хэш для пароля admin/user в дашборде.
# Флаг запрашивает пароль интерактивно — символы не отображаются,
# и пароль не попадает в историю командной оболочки.
# Скопируйте вывод в auth.admin_password_hash или auth.user_password_hash
# в YAML-конфиге.
./bin/tobimaru -hash-password
```

### Что происходит при запуске

1. Разбор CLI-флагов (`-config`, `-version`, `-hash-password`).
2. Загрузка и валидация YAML-конфигурации.
3. Инициализация структурированного логгера.
4. Открытие SQLite-хранилища (если `storage.enabled`).
5. Создание движка состояния и загрузка persisted whitelist/blacklist.
6. Создание движка детектирования; правила регистрируются согласно флагам
   `detection.<rule>.enabled`. Если детектирование включено, но правил нет —
   логируется warning.
7. Создание и запуск capture-пайплайна: включение monitor mode, открытие
   pcap-хэндла, запуск переключения каналов.
8. Регистрация shutdown-хуков (capture stop, storage close, API stop).
9. Запуск consumer-горутин в зависимости от включённых функций:
   - Если детектирование и состояние оба активны — fan-out дублирует фреймы
     в оба пайплайна.
   - Параллельно работают движок детектирования, alert-consumer,
     state-consumer и eviction-горутина.
   - При включённом storage запускается snapshot-writer.
   - Auto-learning выполняется один раз, если включён.
10. Если `api.enabled` — стартуют HTTP-сервер, SSE-хаб и периодический
    публикатор статуса.
11. Процесс блокируется до получения SIGINT/SIGTERM.
12. Shutdown-хуки выполняются в LIFO-порядке с дедлайном 30 секунд.

### Остановка

Отправьте SIGINT (Ctrl+C) или SIGTERM для корректной остановки:

- Движок детектирования и движок состояния дренируют каналы.
- Переключение каналов останавливается.
- pcap-хэндл закрывается.
- WiFi-интерфейс восстанавливается из режима мониторинга.
- HTTP-сервер и SSE-хаб корректно завершаются.
- Все хуки очистки выполняются в обратном порядке (LIFO).

Процесс завершения имеет дедлайн в 30 секунд. Если очистка превышает это
время, оставшиеся хуки пропускаются и процесс завершается.

## Веб-дашборд

Включите одновременно `api.enabled: true` и `storage.enabled: true`, задайте
`auth.admin_password_hash` (сгенерируйте через `./bin/tobimaru -hash-password`) и запустите демон:

```bash
sudo ./bin/tobimaru -config configs/tobimaru.yaml
# Дашборд: http://127.0.0.1:8080
# REST API смонтирован под /api/
```

> **Примечание по безопасности:** API по умолчанию привязан к loopback (`127.0.0.1`).
> Для удалённого доступа всегда используйте реверс-прокси (nginx, Caddy) с TLS —
> никогда не открывайте API напрямую в сеть в продакшене. Пошаговые инструкции см. в
> [Руководстве по настройке обратного прокси](development/reverse-proxy-setup_ru.md).

Дашборд содержит страницы Status, Map (AP и клиенты), Events, Stats, Settings
и Login. Он собирается в `internal/api/web/dist/` и встраивается в бинарь
во время компиляции, поэтому отдельные файлы деплоить не нужно.

Для разработки с hot reload:

```bash
# Терминал 1: бэкенд
sudo ./bin/tobimaru -config configs/tobimaru.yaml

# Терминал 2: dev-сервер фронтенда
cd web && npm run dev
# Открывает http://localhost:5173, проксирует /api на 127.0.0.1:8080
```

```

time=2026-01-15T10:30:00.010Z level=INFO msg="platform capabilities" monitor_mode=true frame_injection=true

```

### JSON-формат

```json
{
  "time": "2026-01-15T10:30:00.000Z",
  "level": "INFO",
  "msg": "Tobimaru WiFi Watchdog starting",
  "version": "1.0.0",

```

```yaml

```

### Отладочное логирование

Включите уровень debug для просмотра информации о каждом фрейме:

```yaml
log:
  level: debug
```

Это создаёт большой объём вывода с каждым разобранным фреймом — полезно для
устранения неполадок, но не рекомендуется для продакшена.

## События безопасности

При включённом движке обнаружения события безопасности генерируются с тремя
уровнями серьёзности:

| Серьёзность | Значение                                                                   |
| ----------- | -------------------------------------------------------------------------- |
| `info`      | Информационное — заметная активность, непосредственной угрозы нет          |
| `warning`   | Подозрительная активность — возможная атака в процессе                     |
| `critical`  | Атака обнаружена с высокой достоверностью — требуется немедленное внимание |

События дедуплицируются по ключу `(event_type, source_mac, bssid)` в пределах
настроенного `dedup_window` для предотвращения усталости от оповещений.

## Устранение неполадок

### "monitor mode not supported"

- Убедитесь, что ваш WiFi-адаптер поддерживает режим мониторинга.
- На Linux: проверьте командой `iw phy <phy> info | grep monitor`.
- На macOS: встроенные адаптеры поддерживают режим мониторинга через BPF
  (CoreWLAN отвечает за переключение каналов).

### "interface not found"

- Проверьте имя интерфейса: `iw dev` (Linux) или `ifconfig` (macOS).
- Убедитесь, что интерфейс не используется другим процессом.

### "permission denied" / "BPF device"

- Запускайте с `sudo` — режим мониторинга и захват сырых пакетов требуют
  привилегий root.

### Высокая загрузка CPU

- Увеличьте `monitor.capture.timeout` для снижения частоты опроса.
- Отключите отладочное логирование.
- Уменьшите количество сканируемых каналов.

### macOS: медленное переключение каналов

- Установите `dwell` в 2 секунды или более.
- Переключение каналов через CoreWLAN на macOS занимает 1–3 секунды;
  установка `dwell` ниже этого значения приводит к тому, что большая часть
  времени тратится на переключение, а не на захват.

### Ошибки конфигурации auth

- При `api.auth.enabled: true` обязательны `storage.enabled: true` и
  непустой `admin_password_hash`. Сгенерируйте хэш с помощью
  `./bin/tobimaru -hash-password` (пароль запрашивается интерактивно).
